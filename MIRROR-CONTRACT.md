# SST3-AI-Harness — Mirror Contract

This repository is the **public scrubbed mirror** of the canonical SST3 governance
framework. The canonical source lives in a private operator repository; this
mirror is generated by a deterministic propagation pipeline so adopters can
inspect, fork, and use SST3 without access to operator-private content.

## Source of truth

| Layer | Lives in |
|-------|----------|
| Canonical SST3 framework (rules, scripts, templates, workflow) | Private operator repository |
| Public mirror (this repo) | `hoiung/sst3-ai-harness` |
| Propagation tool | `propagate-mirrors.py` (canonical-side) |
| Scrubbing rules | A registry of named transforms applied to each mirrored file |

## How propagation works

The canonical side maintains a **drift manifest** (`drift-manifest.json`) that
declares, for every mirrored file:

- The canonical file path
- This mirror's destination path
- A list of named transforms to apply during propagation

Transforms are pure `(text, ctx) -> text` functions. They rewrite or drop
content according to a fixed set of rules. The same canonical file + the same
transform stack always produces the same mirror output (idempotent + content-
addressable).

When canonical content changes, the propagation pipeline:

1. Loads the manifest
2. Reads each canonical file
3. Applies the declared transform stack
4. Writes the result to the mirror destination
5. Reports any drift between the expected mirror content and what's currently on disk

A pre-commit hook on the canonical side blocks edits to mirrored files unless
the propagation pipeline confirms the mirror is in sync. This is how this
public repository stays consistent without manual sync work.

## What gets scrubbed

The transform registry handles, broadly:

- **Path scrubs** — canonical-relative paths (`../<private-repo>/...`) get
  rewritten to mirror-relative paths or replaced with adopter-facing notes
  where the destination is operator-only
- **Issue-URL scrubs** — links to private issue trackers get rewritten to bare
  `Issue #N` references where the project context is operator-only
- **Private-name scrubs** — operator-identity terms and private consumer-repo
  names get replaced with generic placeholders before they reach this mirror
- **Operator-only block drops** — multi-line blocks of operator-only content
  (e.g. credential rotation runbooks, internal-secret rotation procedures) are
  dropped entirely from the mirror
- **`<your-dotfiles-clone>/…` placeholders** — a path beginning
  `<your-dotfiles-clone>/` points at a script or template that lives **only in the
  operator's private dotfiles clone and is NOT shipped in this public mirror**
  (e.g. the propagation pipeline, the per-stage-feedback tooling, the operator
  `install.sh`). You do **not** need a dotfiles clone to use SST3: these refs are
  operator-side workflow plumbing, and where a command's behaviour matters to an
  adopter the relevant rule/schema is described inline next to the reference.

The complete transform implementations are in `scripts/sst3_mirror_utils.py`.
Adopters do not need to mirror the literal canonical drift manifest — the
contract you need to understand is right here.

## Files that exist only in this mirror

Some files exist in this public mirror with no canonical sibling — typically
adopter onboarding guides authored by community contributors. The canonical
side does not need them because they target the public adoption audience
specifically. Examples live under `reference/`.

## Files that exist only in canonical

Some files live only on the canonical side and never propagate to this mirror.
Examples include:

- The private-term mapping table used by the scrubber (it would defeat the
  scrub if it shipped here)
- Canonical-side regression-test fixtures
- Operator-only orchestration scripts (canonical-side automation that has no
  adopter analogue)

The scrubber on this mirror falls through to an identity-fallback (empty
mapping) when the canonical-only mapping table is absent — meaning the public
mirror's scrubber loads cleanly, but its mapping table is empty (which is
correct because the content here has already been scrubbed at propagation
time).

## Reporting drift

If you spot content in this mirror that looks like it leaked through unscrubbed
(an operator-identity term, a private repo name, a path that doesn't make
sense in the public context), please open an issue on this repository. The
canonical side will inspect the manifest's transform stack for that file and
either tighten the transform or document why the surfaced content is
intentional.

## Reading order for adopters

If you're using SST3 to govern your own AI engineering workflow:

1. `workflow/WORKFLOW.md` — the 5-stage workflow definition
2. `standards/STANDARDS.md` + `standards/ANTI-PATTERNS.md` — the rule set
3. `claude/commands/Leader.md` + `claude/commands/SST3-solo.md` — the entry-
   point skills used by Claude Code
4. `templates/` — issue / handover / user-review-checklist templates
5. `ralph/` — three-tier code-review checklists (Haiku / Sonnet / Opus)
6. `reference/` — guides, tool-selection decision tree, lane-selection
   heuristic

You do not need any private operator content to use SST3 as documented here.
