4a. **PRE-DISPATCH FIRST PASS — placeholder/stub grep sweep (Theme 5, #477 AC 2.1)**: BEFORE dispatching Layer-1/2 audit subagents (step 5), run `grep -E 'placeholder|stub|\bTODO\b|if needed|nice-to-have|could be' /tmp/issue_draft_<topic>_<date>.md`. For each hit: replace with concrete spec OR document explicit out-of-scope-with-rationale (no "we might do this later" wording). **Zero hits required before subagent dispatch.** Rationale: subagents that audit a draft full of placeholder/stub language will mirror the placeholders forward as "captured scope" instead of flagging them as gaps — the audit becomes a rubber-stamp. **Finding-to-AC traceability gate (AC 2.3):** (1) extract every Fn AND every Gn from the Stage-1 research file; build a two-column table [finding_id | planned_AC_id]; every row must carry an AC number or explicit `out-of-scope: <rationale>` — gaps with neither block dispatch; (2) walk every imperative phrase ('AVOID', 'MANDATORY', 'required', 'must') in every finding and bind each to a specific AC at sub-element level, not headline level; (3) for every operator-supplied artifact name referenced in a draft AC, run `grep -rl <name>` in the repo — zero hits → AskUserQuestion before writing the AC; (4) if Stage-1 §3 uses unverified-assumption phrasing ('presumably', 'assumed', 'expected'), flag each as an open question to resolve in-draft, not carry forward; (5) **cross-phase artefact consistency pass (#555 Phase 3):** enumerate every announced cluster file, every reserved AP number, and every referenced peer doc in the draft; confirm each maps to a creating AC (cluster file, AP number) or a cleanup AC (peer doc) — none of these are Fn/Gn findings, so the traceability table alone never catches them.
4b. **POST-CORRECTIONS SECOND PASS — same grep sweep (Theme 5, #477 AC 2.2)**: AFTER Layer-2 corrections applied + amendments integrated (step 7), re-run the same grep sweep. **Zero hits required before declaring Stage 2 complete.** Rationale: Layer-2 corrections are inserted via copy-paste from subagent recommendations, which can re-introduce "could be / if needed / nice-to-have" wording even after Pass 1 was clean. Record hit→fix counts in the per-stage feedback file (`SST3-metrics/leader-feedback/feedback-<repo>-<issue>.md` Stage 2 `worked` field). **Re-scan after every manual Edit (#555 Phase 3):** for a public-repo scrub issue or voice-guarded artefact, re-run the leak-scan / em-dash + path-literal scrub after EVERY subsequent manual Edit to the draft — a single pre-creation scrub does not cover later edits; prefer an oracle-exit-code gate over a literal-token grep approximation. **Post-corrections resync (#555 Ralph r3):** after applying any batch of draft corrections — or inserting an AC that adds new files/languages/commit-units — re-read and resync in the SAME pass: (a) the SUMMARY layers end-to-end; (b) the Anti-Bias file list, the commit-atomicity note, and the File-Housekeeping created-files list.

4e. **AC verifiability sweep (Theme 10, #477 AC 2.9)**: before dispatching the layer-1 swarm (step 5), the author reads each AC checkbox and confirms a falsifiable verification command/method exists (binary pass/fail). Rule lives in STANDARDS.md "Workflow Validation Gate" → "AC Verifiability — pre-Stage-3 sub-gate" + issue-template.md "AC Verifiability Gate" subsection. ACs without falsifiable verification get rewritten OR moved to "Items Not Fixed" with rationale BEFORE subagent dispatch — do NOT pass unfalsifiable ACs into the swarm. Pre-swarm rewrites are cheaper than post-swarm rewrites because subagents anchor on whatever scope they receive. **Two required sub-angles (AC 2.2):** (a) **Falsifiability** — for each verify command, mentally simulate a deliberate FAIL state; if the command passes in BOTH the pass and fail states, flag it as toothless and rewrite; (b) **Discriminability** — reject bare-substring greps where an exact-match pattern is available; reject narrative phrases ('output reports', 'reads', 'expects', 'appears to', 'should show') as verify text; for any AC of the form 'add a structural/regression test', the verify MUST be a PAIR — `pytest <file>` exit 0 AND `grep -c '<new assertion string>' <file>` ≥ 1; exit-0 alone proves the test FILE runs, not that it asserts the NEW contract (#555 Phase 3). Author-time preconditions: (c) when a script is named as a verify command, confirm it has an entry-point (`__main__` / argparse / shebang + exit-code contract) before writing it in; (d) when a gate is named as a verify command, confirm the gate's scope rules (exempt-path prefixes, mode skip matrix) admit the file under test; (e) any AC whose only verify is a live external web service or launch-day manual action must ALSO carry a CI-side local gate (parse / grep / exit-code); (f) **hard-gate/exception coherence (#555 Phase 3):** for any new hard-gate AC (a BLOCK/FAIL-on-condition rule), run a sibling self-check — does the gate's language honour every documented exception/escape-hatch AC elsewhere in the draft? A gate and its exception clause are often authored in different passes and can silently contradict; confirm coherence in the same authoring pass. **`command-resolves` sub-check (AC 3.1):** for every Verification clause, (a) dry-run the named binary/path/flag from the target repo's worktree root; (b) replace `grep -P` with `grep -E`; (c) classify vacuous-truth patterns (`all()`/`any()` over empty iterables, Promise without await, grep matching comment-only lines). **AC design-quality checks (AC 4.5):** (1) dry-run each AC verification command against the current PRE-FIX tree and confirm it returns the FAIL value (non-zero exit / the pre-impl count); a verify that passes pre-fix is vacuous and MUST be re-scoped (line-range / exact-pattern / call-site anchor) before dispatch — **mechanise this dry-run with `python3 $SST3/check-ac-discriminability.py <draft.md> --tree-root <repo-root>` (dotfiles#528 AC 6.4): it flags grep/wc/`test` verifies that already pass against the pre-fix tree (exit 1 on any vacuous one) and, post-#555, also hard-flags ALT-AND-RISK / AWK-RANGE-COLLAPSE / FIXTURE-FAIL constructions per the gotcha catalog (g)/(h) below, with a non-blocking `sed -n Np` LINE-ANCHOR advisory; narrative / live-web / script-exec verifies are SKIPPED and remain this manual author step**; run `find tests/ -type d` and verify all cited paths exist; (2) for each AC, ask whether the machine-enforcement gate alone is sufficient to prevent the risk — split any AC containing operator-runtime gates into runtime-independent + runtime-dependent sub-ACs; (3) after any phase-rewriting implementation commit, identify every earlier AC whose satisfying text lived in that block and re-run its verification command (block-rewrite regression check); (4) before posting the Gate-1 close-out checkpoint, re-run each AC being marked complete — do not rely on in-session memory of test results. **(g) verify-command gotcha catalog (#555 Phase 3):** (1) an OR-alternation grep can never assert all-N-present — a count over `a|b|c` is satisfied by one branch matching N times; write a per-term LOOP with a distinct count per term (`check-ac-discriminability.py` hard-flags min-count>=2 alternation counts as ALT-AND-RISK); (2) plain `grep` is BRE — `\|` alternates and bare `|`/`(`/`)` are literal (the dry-run tool emulates this faithfully); (3) an awk `/start/,/end/` range self-collapses to single lines when the start line also matches the end pattern (flagged as AWK-RANGE-COLLAPSE when end==start or end is a literal substring of start); (4) an 'X appears only at Y' claim needs `grep -rniE` over the WHOLE tree plus reading every hit — a case-sensitive or `-l` spot-check misses re-emissions; (5) a NEGATIVE grep (`== 0` after a removal) must be simulated against the mocked POST-FIX state too — a retirement comment or same-named stub re-trips it; (6) an 'N items present' claim needs a paired per-item grep with an explicit count per item, never one aggregate count. **(h) construction edge-cases (#555 Phase 3):** (1) a multi-line/block construct needs a block-scoped extractor (awk range with DISTINCT start/end patterns, or `grep -A`) — a single-line grep silently under-matches; (2) a removed-token grep needs word-boundary + comment-line exclusion, re-verified POST-edit, or it self-trips on its own retirement wording; (3) a shape-literal verify carries an 'or a named-constant/equivalent form' escape clause so a valid alternate implementation is not rejected; (4) prefer a content-anchored grep over `sed -n Np` — a line-anchored verify breaks when an earlier AC inserts lines (the dry-run tool prints a LINE-ANCHOR advisory); (5) a 'runs in CI' AC asserts collection scope (`pytest --collect-only | grep <test>`), not just a green run; (6) when a scanner's input-set can be incomplete, prefer a closure-style verify (`advisories == 0`) over enumerated-target checks that cannot see what the scan missed. **Banned-construct chokepoint rule (#555 Phase 4):** when an AC bans a code construct, prefer a unit-test invariant against a single chokepoint (an allowlist const / helper fn every legitimate use routes through) as the PRIMARY verify; keep the source grep only as a secondary tripwire in the same AC — new call sites bypass an exact-pattern grep, not a chokepoint test. **Key-coarsening collision rule (#555 Phase 4):** for any AC replacing an exact-match key/JOIN with a bucketed/truncated/externally-computed value, or updating a UNIQUE column from an external value — check cardinality (can >1 source row map to one target?) and add a default collision-tolerance AC (dedup / NOT-EXISTS guard / catch+fall-through) in the SAME edit, never a follow-up. **Pipeline-recompute DAG (#555 Phase 4):** for any AC that auto-recomputes or re-runs a pipeline, draw the writer/reader data-flow DAG before writing the AC text. **Char-budget cross-check (#555 Ralph r3):** the sweep re-measures the post-edit draft with `wc -m` against the creation ceiling (step 1's Char-budget discipline) — its own rewrites are edits too.
