## Procedure

Subagents audit everything the main agent produced. Main agent produced the work; subagents verify it. Stage 5 is a POST-IMPLEMENTATION ADVERSARIAL AUDIT — what did the main agent miss? 100% mandatory — every `/Leader` invocation terminates here. It is DISTINCT from Ralph Review (which ran at Stage 4 and verified delivery). Ralph PASS does NOT mean Stage 5 is satisfied — different lens, different class of findings (TB-3 N36).

**Process**:
0. **Step 0 — scope-snippet re-derive (AC 5.5)**: re-derive every cited line range via `grep -n` at HEAD; record the working-tree SHA (`git rev-parse HEAD`); carry `repo_shape`, `documented_false_positives`, and the Tier-A/B deferred-OK list into the scope file. NEVER inherit line ranges or "file X doesn't exist" claims from a handover or prior-stage artefact unchecked (probe-before-assert, AP #29). Line numbers shift between stages; a stale cited range sends the swarm to the wrong place. **Write-time re-derivation extensions (#555 Phase 4):** verify the diff RANGE file-list separately from any `git log --grep` search, declaring interleaved foreign commits; re-derive count-delta findings from the source table's own column (never subagent arithmetic) plus git-blame for introduced-vs-pre-existing; when an operator decision changes the artifact mid-Stage-5, re-derive ALL byte-state numbers; confirm the branch is settled/idle before baselining the audit SHA, and re-verify surviving findings against current HEAD at review-close.
1. Read `graph_applicable` and `invoked_skill` from the Stage 1 research file — do NOT re-classify (TB-2 carry-forward). If `graph_applicable=true`, run `bash $SST3/sst3-code-update.sh` to catch any edits since session start (AP #19 freshness — stale snapshots cause false negatives). Author + run the post-implementation audit swarm via the Workflow tool (DEFAULT; scale to implementation size; Agent/Task = the documented fallback only for a trivial single-angle check). Each subtask covers ONE angle with a RESULT block. One of those angles is a graph-backed audit (NOT a replacement — one audit input among several) when graph available per STANDARDS.md "Structural Code Queries": `bash $SST3/sst3-code-review.sh <default-branch>` (use `main` or `master` per repo default) on the diff, wrapped in a subagent with an UPFRONT warning in the prompt: "Expect 4MB+ JSON output — pipe to file + use `jq`/`python` to slice. Do NOT try to read the full payload." Feed the returned per-file `impacted_callers` counts + untested-function list (+ any `review-error` records — engine failures are findings, not noise; #544) into a subagent prompt. If the `review` output surfaces high-`impacted_callers` (wide-blast-radius) files, PRE-ASSIGN Layer-1 subagent angles by impacted hub (one subagent per hub) rather than generic-angle coverage — hub-anchored angles catch regressions that generic angles miss. Subagent checks whether each flagged item is expected or a regression; main agent verifies against source. Additionally, one subagent angle MUST verify skill-canonical compliance per Double-Guardrail Principle (STANDARDS.md) — the angle uses the comprehensive-walk template per STANDARDS.md "Skill-Canonical Audit Template (Comprehensive Walk)", reads `invoked_skill` + `skill_canonical_files` from the Stage 1 research file, walks every `## ` and `### ` heading of each canonical file against the DELIVERED work (commits + diff), and returns per-section [PASS|FAIL|N/A] with file:line evidence tagged by `source_file`. RESULT block extends with `canonicals_walked` + `section_failures` + `fallback_applied`. Same verify-against-source discipline as the graph-backed audit. See ANTI-PATTERNS.md AP #23. **Twist sub-prompt (#484 V2.4)**: when `invoked_skill ∈ {blog, voice-doc-repo}` AND the delivered diff contains AI-integrated operator-supplied prose, this skill-canonical angle MUST additionally run the STANDARDS.md "Polish vs Twist (Semantic Frame Preservation)" TWIST-forbidden checklist against each delivered polished hunk vs its operator-supplied source (qualifier-add / comparison→verdict / hedge-drop / imposed lens), per-hunk PASS/FAIL — twisting operator-supplied content is an AP #25 regression the heading-walk alone cannot surface; subagent-only, no programmatic detector possible. **Swarm-size heuristic (AC 5.7)**: ≤5 files / ≤50 lines → 3-4 L1 + 1 L2; ≥10 files or a new product module → ≥6 L1. Dispatch as a single parallel batch unless angle B depends on angle A's output. Default tier per STANDARDS.md "Default Tier Assignment per Swarm Role". **Read-only mechanical backstop (#555 Phase 4):** (1) `git status --porcelain` snapshot before/after each read-only leg — any diff auto-flags the leg; (2) a tree-mutating angle (build, fixture create/delete) gets its OWN worktree or runs serialized, never in the shared read-only pool; (3) the subagent-prompt ban covers rm/mv/redirect-to-repo-path COMPOUND commands, not just `rm -rf`, and untracked scratch files are recorded/backed up before the swarm runs; (4) probe-heavy angles write scratch content OUTSIDE the audited worktree. **Doc-realignment scoping (#555 Phase 4):** scope each file-audit agent to the WHOLE file, not a section (cross-section drift is the miss class), and run a main-agent cross-file consistency pass against the single dispatch site before applying per-row fixes. **Operator-script verbatim invocation (#555 Phase 4):** any angle auditing an operator-invoked script RUNS the script's VERBATIM docstring invocation, not only its pytest suite — the documented operator path is exercised empirically. **PowerShell tree-wide parse angle (#555 Phase 4, shape-gated):** for repos bearing PowerShell, dispatch a tree-wide PARSE check as its own Layer-1 angle — NOT diff-scoped — to catch dormant parse bugs in files the current diff never touches (the Stage-1 twin lives in the domain-angle catalogue).
   - **Phase-by-phase scope review**: every issue phase delivered? Every acceptance criterion met?
   - **Goal alignment**: does the implementation solve the stated problem? "Code written" is not "problem solved".
   - **Wiring check**: every new function called by existing code? Every config key read? Every code path handles nulls? No orphaned code? Documentation references correct (file paths, line numbers, URLs all resolve)? Cross-references between docs, configs, and code all connected? Nothing dangling.
   - **Reliability and robustness**: is the implementation reliable and robust (not prone to breakage or failing)? Does it run super fast and safe?
   - **Inefficiency scan**: unnecessary allocations, O(n^2) where O(n) works, redundant DB queries, repeated calculations?
   - **Dead code cleanup**: obsolete/legacy code removed? Commented-out code removed? No backwards-compatibility hacks?
   - **Optimisation opportunities**: faster, simpler, more memory-efficient alternatives?
   - **Deduplication**: copy-pasted code that should be a shared function?
   - **Bottleneck detection**: single points of failure? Blocking operations that should be async?
   - **Memory leak prevention**: unclosed connections, uncleared caches, growing collections, event listener leaks?
   - **STANDARDS.md compliance**: all standards followed? Verification loop checks pass?
   - **Issue body 100% complete**: every checkbox ticked with evidence?
   - **Checkbox-coverage audit (AP #20)**: Proof of Work entries in issue body match every `[x]` box (per STANDARDS.md "Governance Evidence Signal (Canonical)"); Tier A interleave verified against solo-branch `git log` (entry order vs commit order) per opus-review.md Governance Drift Audit (lines 23-28). Any Tier A batching against commit cadence = FAIL and must be flagged in Stage 5 findings. **Evidence standard (#555 Phase 4):** checkbox close-out evidence lines are held to the AC-1.6 verbatim-stdout-or-NOT_RUN standard, same as RESULT blocks; draft-time-ticked boxes are exempt from the PoW-entry requirement. (Blockquote-lift half = incumbent #555 Phase 3 TPL batch — the template's 10 blockquote checkboxes are now top-level and MCP-addressable, retiring the interim gh-issue-edit workaround; `get_issue_events` interleave wiring stays decided-against per STANDARDS §Governance Evidence Signal.)
   - **§3-Deferral Re-Litigation Angle (Theme 7, #477 AC 2.5) — CONDITIONAL**: dispatch this angle ONLY when the user-review-checklist comment posted at Gate 3 has a non-empty §3 "Items Not Fixed" subsection. Subagent reads the user-review-checklist comment, classifies each unchecked/deferred item per the 3-flag taxonomy in `../../templates/user-review-checklist.md` §3: (a) `[deferred-FP: <evidence>]` — confirmed false positive; (b) `[deferred-N/A: <rationale>]` OR no flag at all — feasible fix incorrectly over-deferred (the absence of any flag IS the trigger); (c) `[deferred-tracking-issue: <issue#>]` — intentional user-approved descope to a tracking issue. Only (a) and (c) acceptable; (b) triggers a Stage 5 fix phase per "Fix Everything" guardrail (no deferrals, no scope excuses). Skip-clean if §3 is empty or every item has a (a)/(c) flag. The agent's own §3 entries are subject to the same re-litigation discipline — no self-exemption (#498 F-15). **The user-review-checklist comment is the authoritative §3 location — NOT the Issue body (AC 5.12)** — read the posted Gate-3 comment, not a §3 the agent may have duplicated into the body. Cross-reference: opus-review.md Pre-Merge Precondition Check (~L122). **Risk-class pivot (#555 Phase 4):** when an operator-directed pivot changes a delivered feature's risk class (rate-limit exposure, blast radius, mutation scope), flag it AT PIVOT TIME as needing its own tracked issue under the strict deferral taxonomy — never fold it into a deferred Stage-5 finding. **Un-defer transition (#555 Phase 4):** when the operator explicitly un-defers a previously-deferred finding, the post-fix /Leader 5 round dispatches a FRESH audit swarm scoped to the newly-implemented surface — an un-deferred fix gets the same scrutiny as any other Stage-5 fix, never a lighter check.
   - **Mirror-lane post-merge regression check (#460 Phase 8 W5)**: confirm both lanes (Lane A `propagate-template.py --all --dry-run` exit 0; Lane B `propagate-mirrors.py --validate` exit 0) STILL pass post-merge. If a consumer drifted between merge and Stage 5 (e.g. parallel work landed there), surface in findings.
   - **Production-state verification (AC 5.2) — MANDATORY L1 angle**: run a production-state verification — read the live ledger/log/DB/CI state and verify the stated goal is met post-deploy — NOT just "code-written" (probe-before-assert, AP #29). "The diff adds the row" is a hypothesis until the row is read from the live store. For doc/governance changes the analogue is: the rule is actually loaded/enforced (e.g. `load-stage-rules.sh` emits it, the hook fires), not merely present in a file. **Visual render oracle (#555 Phase 4, shape-gated — visual/brand work):** RENDER the live output (rsvg-convert for SVG, Playwright for pages) and compare element-by-element against the source lockup/brand artifact as the oracle — CSS-token equality is not fidelity.
   - **Sibling-pattern enumeration (AC 5.3)**: for any finding about function X or pattern P, enumerate every sibling file in the same module for the same defect class before returning PASS — use concept-based grep (extract the concept, grep its synonyms), not literal-pattern grep (AP #14e). A parked finding with no assigned angle owner is a dropped finding.
   - **Negative-polarity sweep (AC 5.6)**: for any AC that changes a config value, contractual term, or narrative framing, grep the full doc tree for the SUPERSEDED token (old value / old issue-number / old wording) and assert zero unexpected hits outside intentional historical comment blocks (AP #9).
   - **Writer→reader shape audit (AC 5.14) — conditional**: when the diff touches backend response shapes (JSON field type / dict structure / enum value set / HSET key), dispatch a mandatory L1 angle that locates every frontend consumer via grep and verifies typeof guards, React-invariant safety, and bidirectional type-tolerance across the deploy window. Skip-clean if no response shape changed. Operator-facing content trigger (#555 Phase 4): an AC delivering operator-facing text/UI content fires this angle too — assert the RENDERED FRONTEND, not backend emission.
1a. **Chat Reconciliation (Verifier-Led) at Stage 5 — MAIN-AGENT-OWNED, non-delegable (AC 8.1; Stage 5 previously had ZERO chat-history check).** Extract the operator's raw typed messages with `python3 $SST3/extract-chat-agreements.py --issue <N>` and read the research `## Agreements Log`. Dispatch the THREE-MODEL neutral verifier panel — one Haiku + one Sonnet + one Opus, IN PARALLEL via the Workflow tool's per-agent `model` override (model diversity = different blind spots; distinct from Ralph's SEQUENTIAL code-review) — each given ONLY those raw messages + the agreements log (NOT shown the issue/diff) and the neutral prompt "from these messages, what did the operator ask for / agree to / rule out?". The MAIN AGENT then double-checks each independent interpretation against BOTH (a) the DELIVERED diff/commits AND (b) the issue scope — because the issue itself can have drifted from chat during Stages 2-4, so auditing only against the issue is insufficient; divergence = `invented` (delivered / in-issue, never agreed) / `dropped` (agreed in chat, not delivered) / `inverted` (delivered the opposite of what was agreed). POST the mismatch report into the user-review-checklist `## Chat Reconciliation` section (AC 8.2), then PAUSE for explicit operator approval BEFORE the Stage-5 sign-off. Doctrine: STANDARDS.md "Chat Reconciliation (Verifier-Led)". Untrusted-extractor fallback (#555 Ralph r3): if the extractor's output is empty, errors, or reads content unrelated to this Issue, treat it as UNTRUSTED — hand-capture the operator's verbatim messages into the Agreements Log directly.
2. Layer-2 subtasks in the same Workflow (DIFFERENT angle, per AP#14c): cross-check layer 1. Specifically look for false negatives (problems layer 1 missed). **Raw-tools-only requirement (#447 Phase 5; outside-diff scope AC 5.10)**: at least ONE Layer-2 subagent angle MUST use RAW tools ONLY — direct grep / direct ast-grep / direct find / git log — and explicitly prohibit `sst3-*.sh` invocation. The L2 prompt MUST include: "Look OUTSIDE the diff file list — the wrapper-blind class is precisely files NOT in the diff that the change semantically invalidates." The L2 RESULT block MUST carry `wrapper_invoked: no` as the TOP LINE plus one concrete `single highest-impact fix` finding. This is the audit-time counter-balance to wrapper-lane recall drift: when Stage 4 Verification Loop, Ralph Tier 3, and Stage 5 Layer-1 all use the same wrapper, the swarm becomes blind to wrapper bugs. The raw-only Layer-2 angle is the failsafe. **REACHABILITY sub-angle (#555 Phase 4, named):** before accepting 'no test covers X' / 'X is dead', require a concrete triggering input; for a deletion claim, grep the test tree for the symbol AND run the affected tests (coverage = documented-retained, not safe-to-strip); for cross-language parity goals, require a NaN/non-finite parity test in BOTH suites; for rules-enforcement code, test 5 paraphrases NOT in current fixtures before sign-off. **Canonical-runner cross-check (#555 Phase 4):** a raw-only agent reporting a TEST FAILURE also runs the project's canonical test command and reports both side by side — a failure reproducing only under the non-canonical runner is labelled an environment artifact, not a defect.
3. Main agent reviews ALL RESULT blocks. Verify findings against source. **Verdict-conflict check (AC 5.11)**: any RESULT block with verdict=PASS AND a finding severity > INFORMATIONAL = re-prompt that subagent immediately ("your finding warrants a FAIL — confirm or refute") before accepting the PASS. **Conclusion-flip evidence sweep (#555 Phase 3):** on a Ralph/Stage-4 conclusion-flip (a verdict reversed after checkboxes were closed), re-walk every already-closed AP #20 checkbox-evidence entry for the SUPERSEDED verdict token before Gate-2 merge — artifact regen alone leaves stale PoW lines asserting the old verdict. **Bug-vs-design triangulation (#555 Phase 3):** a bug-vs-design verdict requires 3-source intent triangulation — the architecture doc, `git log -S` on the primitive, and live call-path ownership — with any disagreement between the sources recorded, never resolved by recency or vibe. **Exact-command re-run (#555 Phase 3):** when two L1 angles disagree on a binary outcome, re-run the EXACT command both cited and let its output resolve the conflict — never adjudicate by narrative; for pattern-based scanners, pre-state in the scope snippet that detection is pattern-based, not literal-blocklist.
4. Fix ALL problems. No deferrals. No "low priority". All fixed unless confirmed false positive (document why with evidence). **Doc-drift vs value-tuning split (#555 Phase 4):** when a finding conflates a fixable doc-drift with an operator-territory value-tuning decision, fix ONLY the doc-drift and surface the value question as a JBGE-DEFERRED item with an explicit trigger — never silently absorb the re-tune into scope.
5. If fixes were applied: run regression tests AFTER the fixes. This is mandatory — fixing code can introduce new regressions. Verify no regressions before declaring clean.
6. If fixes applied: commit, push, update the issue.
7. If no fixes needed: run regression tests anyway to confirm clean state. A Stage-3 'settled / fails-safe' claim never exempts Stage-5 re-testing (#555 Phase 4).

8a. **MANDATORY closing-summary comment (dotfiles#528 AC 3.1 — "the final comment is always forgotten").** BEFORE the sign-off, post an agent-authored closing-summary comment to the Issue carrying the machine-detectable sentinel **`<!-- sst3-closing-summary -->`** on its own line. Exit 0 mandatory. The Layer-B `stage5-completeness.yml` server-side replay enforces C18 identically (won't fire until the GHA monthly limit resets — the manual 8b run is the live gate meanwhile). Only after 8b passes → SIGN-OFF.

**DO**: Require specific findings from every subagent (file:line, evidence). Fix everything found. Run regression tests.
**DON'T**: Accept "looks fine" from subagents. Defer fixes. Skip regression tests. Fire-and-forget. Create new GitHub issues autonomously — propose Stage 5 findings as comments on the parent issue; creating new issues requires explicit user authorization in chat (AP #21, added #431 Phase 2b). **Follow-up candidates (#555 Phase 4):** post follow-up work candidates as comments AT THE STAGE they are discovered (filing stays operator-gated per AP #21) — batch-deferring the set to close-out inflates close-out load and loses discovery context.
